# 部署与运维

命令默认在仓库根目录执行。首次安装的两种方式见[项目 README](../README.md)；本文补充配置、发布与日常维护。运行需要 Docker Linux 引擎及 Compose v2，生产建议使用具备 HTTPS 反向代理的 Linux 服务器。

## 镜像与 Compose 文件

Docker Hub 仓库：[nicccce/acm-labrank](https://hub.docker.com/r/nicccce/acm-labrank)。当前发布 `linux/amd64` 镜像；ARM 主机可自行构建原生镜像，或明确使用 Docker 的 amd64 模拟运行，原生 ARM 构建尚未验收。

| 镜像标签 | 用途 |
| --- | --- |
| `1.1.0` | 固定版本，Web、迁移、管理员引导共用 |
| `worker-1.1.0` | 同版本通用 Worker，负责 CF、洛谷和 QOJ，包含 Chromium、Xvfb、VNC/noVNC |
| `latest` / `worker` | 对应最近发布的应用和 Worker 镜像；生产建议固定版本 |

| 配置文件 | 用法 |
| --- | --- |
| `compose.yaml` | 默认拉取 Docker Hub 的应用、通用 Worker 和 PostgreSQL 镜像，无本地 build 和源码挂载 |
| `compose.build.yaml` | 追加到基础配置后，从源码构建 `acm-leaderboard:local` 和 `acm-leaderboard:worker` |
| `compose.dev.yaml` | 本地 Node 开发时追加，仅发布回环数据库端口 5433 |

QOJ 远程桌面来自通用 Worker 镜像。仓库不包含专用中继服务；Worker 默认直连平台，需要代理时为标准的 `QOJ_BROWSER_PROXY_SERVER` 指定受控 endpoint。数据库迁移 SQL、Drizzle meta、锁文件和测试样本属于源码，必须保留并提交。

## 配置与初始化

`scripts/setup.mjs` 生成 `.env`、数据库随机密码和四个 Secret，不输出密码。已有文件保留；已有管理员时 bootstrap 不改密码。`--directory` 可将配置写到独立部署目录，模板始终从脚本所在源码或镜像读取。

只部署发布镜像时，可使用独立目录，只需准备 `compose.yaml` 并运行 README 中的容器初始化命令。无需安装 npm 依赖，也不需要把源码挂载到应用容器。

| `.env` 变量 | 默认值 / 部署要求 |
| --- | --- |
| `ACM_IMAGE_REPOSITORY` | `nicccce/acm-labrank`，可改为自己的镜像仓库 |
| `ACM_IMAGE_TAG` | `1.1.0`；Worker 镜像自动使用 `worker-` 前缀 |
| `APP_URL` | `http://localhost:3000`；正式部署填实际 HTTPS Origin |
| `WEB_BIND_PORT` | `3000`，只绑定宿主回环地址 |
| `POSTGRES_DB` / `POSTGRES_USER` | 默认均为 `acm` |
| `POSTGRES_PASSWORD` | setup 自动生成；已有库不能只改 `.env` 密码 |
| `DATABASE_URL` | 本地 Node 开发连接 5433；Compose 自动改为容器内 `db:5432` |
| `ADMIN_BOOTSTRAP_USERNAME` | `admin`，仅首次管理员创建使用 |
| `SESSION_ENCRYPTION_KEY_FILE` | 宿主密钥路径，默认 `.secrets/session-encryption-key` |
| `ADMIN_BOOTSTRAP_PASSWORD_FILE` | 宿主初始管理员密码路径 |
| `SYNC_ENABLED` / 平台间隔变量 | 仅初始化缺失数据库策略，运行设置在管理页修改 |
| `QOJ_DESKTOP_PORT` | `6080`，只绑定宿主回环地址 |
| `QOJ_VNC_URL` | 浏览器访问的 noVNC URL，远程用本地隧道或受控 HTTPS 代理 |

保护并备份 `.env` 和 `.secrets`，尤其不要重新生成正在使用的会话加密密钥。Linux 下 setup 将 `.secrets` 设为 `0700`，其中 Secret 文件设为 `0444`：宿主的其他用户不能遍历受保护目录，而非 root 应用可以读取单独挂载到 `/run/secrets` 的文件。文件挂载保留宿主权限，不能依赖 Compose 的 `uid/gid/mode` 自动修正。参见 [Docker Secrets 文档](https://docs.docker.com/compose/how-tos/use-secrets/)及 [services secrets 限制](https://docs.docker.com/reference/compose-file/services/#secrets)。Windows setup 使用当前用户、目录所有者和 SYSTEM 的受限 ACL。

## 首次启动与健康状态

启动依赖为 `db healthy → migrate 成功 → bootstrap 成功 → web / worker`。迁移及管理员引导是一次性容器，正常结果为 `Exited (0)`；Web 和 worker 持续运行并应显示 healthy。

```bash
docker compose ps -a
docker compose logs --tail=100 migrate bootstrap web worker
curl -f http://localhost:3000/api/health/ready
```

标准 Compose 已包含浏览器 Worker。源码部署只需追加 `-f compose.build.yaml`，无需组合平台专用配置文件。

首次登录管理员后，检查 `/admin/collection` 的平台、榜单日期、自动更新与采集开关。采集默认暂停；确认成员绑定、平台登录和核验后再开启。生产无需 seed；测试环境可执行 `docker compose run --rm --no-deps seed`，测试密码在 `.secrets/member-test-password`，该操作会创建测试账号。

## HTTPS 与 QOJ 远程登录

Nginx/Caddy 等反向代理转发到宿主 `127.0.0.1:3000`，保留原始 Host 和正确的转发信息；把 `APP_URL` 设为同一 HTTPS 地址后重建应用容器。应用依此校验 Origin 并设置 Secure Cookie。反向代理若在其他容器，应通过共同网络连接 Web 的 3000 端口。

QOJ 使用通用 Worker 容器内的专用浏览器，CDP 与原始 VNC 只在容器回环监听；宿主只发布回环 noVNC 端口 6080。远程管理员在自己电脑建立隧道：

```bash
ssh -N -L 3000:127.0.0.1:3000 -L 6080:127.0.0.1:6080 管理员@服务器
```

用 `http://localhost:6080/vnc.html?autoconnect=1&resize=scale` 打开桌面，从服务器 `.secrets/qoj-vnc-password` 本地读取并输入密码。在 Chromium 登录 QOJ 后，回到站点 `/admin/connections` 点击核验。若站点通过 HTTPS 访问，默认 HTTP iframe 可能被浏览器拦截，直接在独立页面打开隧道桌面，或为 noVNC 配置受控 HTTPS 地址并更新 `QOJ_VNC_URL`。

QOJ profile 使用 tmpfs。容器重建或重启可能丢失外站登录；升级前安排重新人工登录。仅构建或拉取镜像不影响现有会话，详见 [QOJ 运行手册](QOJ采集流程与技术维护.md)。

## 自己构建与推送 Docker Hub

源码构建使用版本化依赖及两个多阶段目标，Dockerfile 自带 Node.js/pnpm。先完成 `pnpm check`，或者在已构建镜像执行 `docker run --rm --entrypoint pnpm acm-leaderboard:local check`。以下在 Linux shell 操作，替换镜像仓库和版本号：

```bash
IMAGE=你的DockerHub用户名/acm-labrank
VERSION=1.1.0
REVISION=$(git rev-parse HEAD)
docker build --target runtime --build-arg VCS_REF="$REVISION" \
  --build-arg APP_VERSION="$VERSION" -t "$IMAGE:$VERSION" .
docker build --target worker-browser --build-arg VCS_REF="$REVISION" \
  --build-arg APP_VERSION="$VERSION" -t "$IMAGE:worker-$VERSION" .
docker login
docker push "$IMAGE:$VERSION"
docker push "$IMAGE:worker-$VERSION"
docker tag "$IMAGE:$VERSION" "$IMAGE:latest"
docker tag "$IMAGE:worker-$VERSION" "$IMAGE:worker"
docker push "$IMAGE:latest"
docker push "$IMAGE:worker"
```

镜像记录 `org.opencontainers.image.source/revision/version` 以追溯源码。部署端在 `.env` 设置 `ACM_IMAGE_REPOSITORY` 和 `ACM_IMAGE_TAG`，使用基础 Compose 拉取即可；应用与 Worker 必须使用匹配版本。网络受限时可通过 `--build-arg NPM_REGISTRY=https://可信npm源/` 指定源；浏览器 apt 源可用 `DEBIAN_MIRROR`、`DEBIAN_SECURITY_MIRROR`。

## 备份、升级与停止

从 1.0.0 更新到 1.1.0 的完整服务器操作命令见[升级到 1.1.0](升级到1.1.0.md)。版本标签发布会通过 `.github/workflows/release.yml` 在独立 PostgreSQL 上检查旧库升级及业务回归，构建应用和 Worker，并在镜像中验证 HTTP、桌面／窄屏管理流程，成功后推送版本标签及 `latest`／`worker` 别名。Docker Hub 凭据保存为仓库 Actions Secrets，不进入源码。

升级前在管理页暂停采集，等待活动任务结束。备份完整数据库和受保护的 `.env/.secrets`。以下数据库导出方式适用于 Bash 和 PowerShell，避免二进制备份通过 shell 文本重定向损坏；先创建本地 `.local` 目录。

```bash
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc -f /tmp/acm-backup.dump'
docker compose cp db:/tmp/acm-backup.dump .local/acm-backup.dump
docker compose exec -T db rm /tmp/acm-backup.dump
```

不要把备份、账号密码、Cookie 或会话密钥提交到 Git。数据库备份必须连同当时密钥一起受控保存，否则恢复后无法解密平台会话。

从上一版 `0012_scoring_settings`（13 项迁移）升级到用户管理版，使用新源码里的更新脚本。先在 `/admin/collection` 暂停采集并等待活动任务结束，保留原部署目录、Compose 项目名、`.env`、`.secrets` 和数据库卷。发布镜像方式将 `.env` 的 `ACM_IMAGE_TAG` 改为**实际已经发布的目标版本**，然后执行：

```bash
node scripts/update.mjs --check
node scripts/update.mjs
```

源码部署使用 `node scripts/update.mjs --build --check` 和 `node scripts/update.mjs --build`。脚本支持 Node.js 22+，不需要宿主安装 pnpm；`--directory /原部署目录` 用于配置位于另一目录的部署。脚本从源码目录读取当前迁移版本，拒绝目标镜像仍是旧版本；更新时应先确认对应版本镜像已经发布。

`--check` 准备目标镜像，先读取镜像中的 `packages/db/upgrade-protocol.json` 和迁移目录确认版本，此步骤不连接数据库。旧版迁移脚本会忽略 `--check`，因此没有本轮协议标记的旧镜像会在调用迁移前被拒绝。然后只读核对数据库迁移、队列版本和采集暂停状态，不停服务、不执行 DDL。正式更新校验当前数据库容器、原 `pgdata` 卷与凭据，备份 `.env`、Compose 文件和实际使用的 Secret 文件，停止 Web/Worker 后导出完整 PostgreSQL 自定义格式备份，并以 `pg_restore --list` 核对格式。备份及 SHA-256 清单保存于受保护的 `.local/upgrade-时间-随机值/`。随后每次都启动新的 `migrate`、`bootstrap` 一次性容器，成功后仅启动 Web/Worker 并等待健康检查；数据库服务不重建。备份包含敏感数据，应受控另存到独立介质，并演练完整恢复，格式校验不代替恢复演练。

`.local/update.lock` 防止同一目录并发更新。异常退出遗留锁时，先确认没有更新进程，再移除该锁。若备份、迁移、引导或健康检查失败，脚本退出并保留备份；服务可能仍停止或处于不健康状态。脚本不自动恢复旧数据库或启动旧应用，避免覆盖更新期间的数据或使用不兼容版本。

Worker 容器更换可能使 QOJ 的内存浏览器登录失效，需要重新人工登录；原数据库中的加密平台会话保留。需要保留现有 Chromium 的特殊更新使用[原位更新说明](个人后端与Web登录.md)，手工执行备份及下述迁移命令，不运行会替换 Worker 的常规更新脚本。迁移不会重置采集或计分设置，更新验证完成后由管理员恢复采集。

### 增量迁移及默认值

`scripts/setup.mjs` 仅初始化缺失配置，继续保留已有凭据；数据库升级统一走 `pnpm db:migrate`，不能用重新初始化、schema push 或 seed 代替。用户管理版追加 `0013_mean_vanisher`，从 13 项增至 14 项，旧迁移 SQL 和元数据保持不变。

| 新字段／表 | 原记录的值 | 新记录默认值 |
| --- | --- | --- |
| `users.is_starred` | `false` | `false` |
| `users.deleted_at` | `NULL` | `NULL` |
| `users.must_change_password` | `false` | `false` |
| `teams.is_starred` | `false` | `false` |
| `user_management_events` | 新增空表 | 按管理操作追加记录 |

PostgreSQL 使用 `ADD COLUMN ... DEFAULT false NOT NULL` 为旧记录补齐布尔值；删除时间保持可空。没有对既有 `users/teams` 执行全表 UPDATE、删除、重建或重新插入；用户 ID、用户名、真实姓名、密码哈希、原封禁状态、会话、平台绑定、成绩、成员关系和设置均保留。原用户不会因为升级被强制改密，原封禁用户也不会解封。重复迁移由 Drizzle 历史跳过，不会将随后修改的打星、删除时间、改密要求恢复为初始值。

仅迁移数据库，或使用本地 Node 开发部署时，在备份和停止旧应用后运行：

```bash
pnpm db:migrate --check
pnpm db:migrate
```

Compose 手工迁移须使用目标版本的镜像：`docker compose run --rm --no-deps migrate pnpm db:migrate --check`，再执行 `docker compose run --rm --no-deps migrate`。迁移历史必须是当前代码历史的完整前缀；脚本核对时间戳和 SQL SHA-256（允许 Windows/Linux 换行差异），拒绝较新的库、修改过的历史或缺失迁移记录的既有业务表。不要手工改迁移记录来绕过检查，也不要给全部 DDL 加 `IF NOT EXISTS` 隐藏结构不一致。

业务 DDL 与迁移记录在同一事务中提交，失败全部回滚；迁移使用数据库锁阻止并发，表锁等待超过 10 秒会中止，单条 SQL 限时 5 分钟。队列 schema 与缺失设置初始化属于后续阶段，使用各自的事务／幂等操作；该阶段失败可修复原因后重复执行，不能认为整个部署均已回滚。最终 readiness 核对 14 项迁移、队列版本和新字段类型、默认值、空值约束。

`pnpm upgrade:verify` 在随机命名的独立库中重建上一版，填入旧用户、密码、会话、绑定、成绩、游标、队伍和自定义设置，对全部原有公共表的原字段逐表核对数量及摘要，验证默认值、重复升级、SQL 失败回滚、迁移锁、历史异常与旧密码／会话继续有效。成功删除测试库，失败保留库名；运行账号需要创建测试数据库权限。不会迁移正式库。

升级失败先检查 migrate/bootstrap 日志；迁移成功后不能假定旧版本兼容新数据库。需要恢复时，在独立环境恢复经过核验的数据库备份、对应密钥和匹配镜像；不要在原库上盲目降级。上线前应演练一次恢复。

`docker compose stop` 停止容器，`docker compose down` 删除容器和网络但保留 `pgdata` 命名卷；`down -v` 会删除数据，仅适用于明确废弃的测试环境。生产不要改变 Compose 项目名或卷名，否则会接入另一份数据库卷。

## 常见故障

| 现象 | 检查与处理 |
| --- | --- |
| 镜像拉取失败 | 确认仓库、版本和 Docker Hub 网络，私有镜像先 `docker login` |
| 没有匹配平台 manifest | 当前发布 amd64，ARM 环境按源码方式构建并验证 |
| migrate/bootstrap 失败 | 看一次性容器日志，检查数据库凭据、Secret 是否存在及读取权限 |
| Web readiness 503 | 确认迁移及 pg-boss schema 完成，数据库健康且镜像版本匹配 |
| 登录或写操作 Origin 不匹配 | 确认 `APP_URL`、浏览器地址和代理 Host 配置一致 |
| 修改环境采集间隔却未生效 | 运行策略保存在数据库，在管理员页面/API 修改 |
| QOJ 桌面/登录失效 | 检查 worker/noVNC 和隧道，重建容器后重新人工登录 |
| Docker Desktop 无法直连平台 | 查看 `.env.example` 的 Node 出口代理及可选 `QOJ_BROWSER_PROXY_SERVER`，Linux 的 host.docker.internal 需显式配置 |

## 仓库维护约定

依赖目录、`.next`、TypeScript 增量缓存、覆盖率、日志、备份、`.local` 和工具工作树由 `.gitignore` 排除；同类文件由 `.dockerignore` 排除构建上下文。删除了依赖旧本机镜像的 `Dockerfile.cached` / `compose.cached.yaml`。历史验收保留在 `docs/archive`，不作为当前运行状态证明。

`.local` 中的数据库备份和诊断结果保留在本地，不批量删除；现有 Git 工作树也保留，避免丢失独立开发内容。新增临时验证文件放到 `.local`，可复用的检查脚本才进入 `scripts`。
