# 从 1.0.0 保留数据升级到 1.1.0

发布镜像：`nicccce/acm-labrank:1.1.0`（Web／迁移）和 `nicccce/acm-labrank:worker-1.1.0`（采集及浏览器），平台为 `linux/amd64`。源码标签为 `v1.1.0`。两个镜像必须一起更新。

本版增加用户／队伍打星、管理员用户管理和密码重置／修改。升级只追加第 14 项业务迁移 `0013_mean_vanisher`，保留原用户、姓名、密码、封禁状态、会话、绑定、成绩、队伍关系、采集游标、计分及采集设置。新增字段的旧记录默认值：

| 字段 | 默认值 |
| --- | --- |
| `users.is_starred` | `false` |
| `users.deleted_at` | `NULL` |
| `users.must_change_password` | `false` |
| `teams.is_starred` | `false` |

另外新增空的用户管理操作记录表。重复升级会跳过已经提交的迁移，不会把后续修改的状态重置为默认值。

## 准备

先在旧站 `/admin/collection` 暂停采集，等待正在执行的采集及登录任务结束。整个更新期间不要重新开启采集。

在**原部署目录**操作，保留原 `.env`、`.secrets`、Compose 项目名及数据库卷。若此前使用了 `COMPOSE_PROJECT_NAME` 或自定义 Secret 路径，继续使用原值。不要新建另一套配置，不要运行 seed、数据库初始化或 `docker compose down -v`。

源码以 Git 管理的服务器执行以下命令；如果有本地修改，Git 会要求先处理冲突，应保留并核对原来的配置，不能用强制覆盖绕过：

```bash
cd /你的原部署目录/acm-labrank
git fetch origin tag v1.1.0
git checkout v1.1.0
cp -p .env .env.before-1.1.0.bak
chmod 600 .env.before-1.1.0.bak
```

编辑 `.env`，只将 `ACM_IMAGE_TAG` 设为 `1.1.0`。保留 `POSTGRES_*`、`APP_URL`、端口、镜像仓库及密钥路径原值。若该键原来不存在，新增这一行即可：

```dotenv
ACM_IMAGE_TAG=1.1.0
```

## 自动备份及更新（推荐）

宿主有 Node.js 22+ 时执行，不需要 pnpm：

```bash
node scripts/update.mjs --check
node scripts/update.mjs
docker compose ps
```

第一条准备新版镜像，核对镜像协议、迁移历史、原数据库卷和采集暂停状态，不停服务、不执行 DDL。第二条先备份 `.env`、Compose 和所有实际使用的 Secret 文件，停止旧 Web／Worker，再导出数据库并校验归档格式和 SHA-256；备份成功后才执行增量迁移和幂等的管理员引导，最后只更新 Web／Worker 并等待健康检查。数据库容器和卷不重建，已有管理员密码不重置。

备份路径为 `.local/upgrade-时间-随机值/`，其中 `database.dump` 是完整 PostgreSQL 自定义格式备份，`secrets/` 是密钥副本，`manifest.json` 记录摘要及原容器信息。目录包含敏感数据，另存到受控的独立存储；`pg_restore --list` 格式校验不能代替恢复演练。

源码自行构建的服务器，两条脚本命令均加 `--build`。配置位于其他目录时用 `--directory /原部署目录`；仍应从匹配的 1.1.0 源码执行。

## 只有 Docker 的服务器

以下为 Linux Bash 命令，每条都必须成功后继续。先完成上面的暂停采集、更新源码和修改镜像标签。手工流程需要自行检查原数据库容器、卷名及配置一致，不具备自动脚本的全部防护；可安装 Node.js 后使用推荐方式。

```bash
set -euo pipefail
umask 077
BACKUP="$PWD/.local/upgrade-manual-$(date -u +%Y%m%dT%H%M%SZ)-$$"
mkdir -p "$BACKUP"
cp -p .env .env.before-1.1.0.bak compose.yaml "$BACKUP/"
cp -a .secrets "$BACKUP/"
```

如 `.env` 指定了 `.secrets` 以外的 Secret 文件，也须复制这些实际使用的文件到备份目录。确认数据库仍连接原卷，并拉取新版应用及 Worker：

```bash
docker compose ps db
docker inspect "$(docker compose ps -q db)" \
  --format '{{range .Mounts}}{{if eq .Destination "/var/lib/postgresql/data"}}{{.Name}}{{end}}{{end}}'
docker compose pull migrate worker
docker compose run --rm --no-deps migrate pnpm db:migrate --check --require-paused
```

输出应显示迁移总数 14，旧版已完成 13，待执行 `0013_mean_vanisher`。只读检查必须使用刚拉取的 **1.1.0** 镜像，1.0.0 的迁移脚本不支持 `--check`。

停止旧应用并导出、校验备份。归档直接在数据库容器内写成二进制文件，通过 `compose cp` 取出，避免 shell 文本重定向损坏：

```bash
docker compose stop web worker
ARCHIVE="/tmp/acm-upgrade-1.1.0-$$.dump"
docker compose exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc -f "$1" && pg_restore --list "$1" >/dev/null' \
  sh "$ARCHIVE"
docker compose cp "db:$ARCHIVE" "$BACKUP/database.dump"
sha256sum "$BACKUP/database.dump" > "$BACKUP/database.dump.sha256"
docker compose exec -T db rm "$ARCHIVE"
```

备份成功后执行迁移，再启动匹配的新应用。`--no-deps` 确保不会顺带重建数据库；每次显式运行迁移，避免复用旧的已退出 migrate 容器：

```bash
docker compose run --rm --no-deps migrate pnpm db:migrate --require-paused
docker compose run --rm --no-deps bootstrap
docker compose up -d --no-deps --wait web worker
docker compose ps
```

## 更新后检查及失败处理

确认 Web／Worker 健康，原账号可登录，绑定、成绩、队伍和计分设置仍在；检查 `/admin/users`、`/admin/teams` 及个人打星开关。旧用户不会被强制改密或自动打星，旧封禁用户继续保持封禁。确认后在管理页恢复采集。

Worker 更换可能使 QOJ 的浏览器登录失效，需要人工重新登录和核验；数据库中的绑定、成绩和加密会话仍保留。

若任一步失败，停止后续操作，检查 `docker compose logs --tail=100 web worker` 及失败的一次性容器输出。自动脚本保留备份，服务可能仍停止。业务迁移的 DDL 与历史记录在同一事务内，失败回滚；后续队列初始化或应用启动失败不代表已经完成的迁移回滚。修复原因后可重复执行更新。

不要删除数据库卷、改数据库凭据、手工改迁移历史或直接换回旧应用。需要恢复时，在独立环境恢复经过核验的数据库备份、对应密钥及匹配旧镜像，确认后再切换。详细原理及限制见[部署与运维](部署与运维.md)。
